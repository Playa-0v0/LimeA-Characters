# 音色绑定与已有作品资料整理

## 本机音色档案

音色档案名称由用户在 LimeA 本机自定义，例如“昔涟”；模型名称和供应商音色 ID 是档案里的独立字段，不能把显示名当成音色 ID。一个服务可以配置多份档案。

1. 打开“设置 → 语音合成”，在“音色档案”中新建并命名档案，选择语音服务和模型，填写该服务实际可用的音色 ID，以及支持的其他参数，保存档案。服务密钥由用户在界面中自行填写，不要求用户把密钥发到聊天或写进角色文件。
2. 需要试听时使用已保存的档案；具体模型、音色列表、参考音频或复刻能力取决于所选服务。不要凭角色名猜测音色 ID，也不要假称已试听或已复刻。上传或复刻使用用户有权使用的音频，并以用户明确请求和实际服务能力为前提。
3. 打开“设置 → 角色管理”，选择角色，在“朗读音色”中选择该档案并保存音色绑定。名称相同与否不决定绑定，实际绑定使用档案稳定标识。
4. “启用语音合成”“自动朗读”“边合成边播放”是全局朗读行为。没有绑定音色的角色不自动朗读；手动朗读会提示绑定。档案被删除或服务不可用时不切换其他声音。

绑定只保存在本机，不写入 `character.json`、提示词或世界书，也不随 `.limea` 导出。分享或导入到其他设备后，在目标设备创建或选择档案并重新绑定。编辑绑定不创建角色卡修订。界面不一致时按目标版本实际支持情况说明；不可绕过安全存储直接读取密钥或修改数据库。

## 已有作品：从资料到角色卡

1. 确认作品、角色、语言、版本和剧透范围；有歧义时根据用户提供的线索核对，不把同名角色混为一谈。用户提供的原作资料优先使用；需要补充时使用当前环境可用的搜索和网页读取能力。无法联网或页面不可访问时说明缺口，不伪造检索结果。
2. 优先查作品官方角色介绍、原作故事或官方台词，再用相关 Wiki 的角色、剧情、词条和语音页面定位细节。核对页面标题、作品版本、上下文和更新时间；对关键事实尽量追溯原出处。Wiki 可能有错误、不同译名或剧透，冲突时列明分歧和来源，不把推测当成定论。
3. 记录资料标题、链接、涉及章节或语音条目、语言及访问日期。先提炼身份、动机、关系、价值观、表达方式和具体行为证据，再写 `soul.md`；将证据不足的推断标明或留空。当前助手的任务事实以用户输入和实际工具结果为准，不把虚构经历写成现实操作。
4. 按人物、地点、事件等主题组织世界书。每条只放相关事实，用用户可能输入的正式名、别名作触发词，避免常见词误触发。保存稳定条目标识；版本有冲突时按用户选定版本编写。
5. 在官方台词或 Wiki 语音页面核对说话者、场景、原文和译文。选少量能够展示不同语气的短例，记录来源；受版权限制时用概述或原创风格示例，不大段复制。不能核实的内容不要标为原作原话，也不要把意译写成逐字引用。
6. 给用户交付事实与来源清单、明确的推断/缺口和角色文件；如果要把来源说明放进角色卡，先将说明文件声明为 `readme`，不要在容器中放未声明文件。未确认实际音色前，保持角色无音色绑定。

检索时可组合“作品名 + 角色名 + 官方角色介绍”“作品名 + 角色名 + Wiki + 语音/故事/剧情”，并用原名、译名或别名交叉查询；从搜索结果打开具体页面核对，不把搜索摘要当作已验证原文。若页面指向游戏内剧情、官方视频或角色语音，再回到对应出处确认。

整理人设时把证据、归纳和落笔分开。例如：资料显示角色曾主动帮助迷路旅人，这是可记录的事实；“面对求助时愿意先了解对方需求”是可注明依据的行为归纳；一次行为不足以证明她“总是无私帮助所有人”。把有足够依据的归纳写成自然、可执行的相处方式，不要求模型照搬剧情或台词。
